> 规矩：① 只收我自己读过、且 URL 能打开的 ② 每条写「借了什么」，不写「参考了 XX」这种糊账 ③ 链接失效就删行，不留死链。

## 1. 检索打分（`tools/memdb.py` 的 `search_rows`）

我们现在的公式（`memdb.py:215` 与 `:228-235`）：

```python
w = {t: 1.0 / ((df[t] + 1) ** 0.6) for t in toks}   # 稀有权重
cover = 0.6 + 0.4 * len(set(matched)) / len(set(toks))  # 覆盖率
if rare not in matched: base *= 0.25                  # 最稀有词门控
s = base * cover * (1 + 0.3 * imp) * recency(d[2]) * kw_boost
```

- **Okapi BM25** —— 词频饱和（`tf` 涨到一定程度收益递减）+ 逆文档频率（`idf`，词越常见越不值钱）+ 文档长度归一化。我们只借了 `idf` 那一半：`1/(df+1)^0.6` 是 `idf` 的简化，指数 `0.6` 是我们自己压的（不用 `log`，省得算），**没实现 `tf` 饱和和长度归一化**。
  - 官方文档口径：<https://www.sqlite.org/fts5.html#the_bm25_function>（看它怎么描述 `bm25()` 返回「越小越匹配」）
  - <https://en.wikipedia.org/wiki/Okapi_BM25>
- **Reciprocal Rank Fusion（RRF）** —— 多路召回排序融合：每路只贡献 `1/(k+rank)`，不用分数可比。**我们没用**，但「以后要加语义检索」时这是最省事的两路合并法（关键词一路 + 向量一路）。
  - <https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf>
- **rank_bm25** —— Python 里 BM25 的可读实现，想核对公式对不对时对照它最快。
  - <https://github.com/dorianbrown/rank_bm25>

### 1.1 片段层的 BM25（`tools/frag.py` 的 `score`，2026-10-20 补）

`frag.py` 这一套比 `memdb.py` 更接近标准 BM25：`k1=1.2`、`b=0.75`、`idf = log((N+1)/(df+0.5))`、标题词双倍加权。

- **Okapi BM25 的 tf 饱和与长度归一化** —— 长片段不该因为字多就白拿分，长片段里同一个词的边际收益要递减。这就是 `c + k1 * (1 - b + b * dl / avg)` 那一项。
  - <https://en.wikipedia.org/wiki/Okapi_BM25>
- **BM25+（Lv & Zhai）** —— 原版 BM25 对**长文档里的短查询**有下界缺陷：词出现了却可能因为长度惩罚拿到接近 0 的分，`δ` 加一个下界项修掉它。我们的片段只有 1～4 行，长度差不大，暂不加 `δ`；等片段变长再加。
  - <https://www.ideals.illinois.edu/bitstream/handle/2142/34306/Lv_Yuanhua.pdf?sequence=1&isAllowed=y>
- **查询同义扩展（query expansion / synonym filter）** —— 搜索引擎的标准做法：把口语说法映射到索引里的正式词，扩出来的词**权重打折**，只加召回不改排序主次。我们照这条在 `tools/synonyms.py` 里写了 `ALIAS_GROUPS`，`EXPAND_W = 0.45`。
  - Lucene `SynonymGraphFilter`：<https://lucene.apache.org/core/9_0_0/analysis/common/org/apache/lucene/analysis/synonym/SynonymGraphFilter.html>
  - Elasticsearch 同义词文档：<https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis-synonym-tokenfilter.html>
- **用 recall@k 与 MRR 量命中率，而不是凭感觉** —— 「命中率不够」必须先有数，否则改打分等于瞎调参。`tools/recall_eval.py` 的 22 条评测集与 `recall@1/@3/@5`、`MRR` 指标就是照这套评测惯例做的。
  - MRR 定义：<https://en.wikipedia.org/wiki/Mean_reciprocal_rank>
  - BEIR（零样本检索评测基准，验证了「BM25 是很强的基线」）：<https://arxiv.org/abs/2104.08663>

## 2. 三层记忆结构（`90` §1 的 core / archival / recall）

- **MemGPT / Letta**（arXiv 2310.08560）—— 把上下文当「内存」、外部存储当「磁盘」，靠分页与换入换出管理记忆；我们借的是**分层**这个骨架（每轮在 / 按需读 / 翻历史），**没借它的自编辑循环**（我们靠人触发写，不靠模型自己搬页）。
  - <https://arxiv.org/abs/2310.08560>
  - 工程侧：<https://docs.letta.com>
- **Generative Agents**（arXiv 2304.03442）—— 检索三因子 `recency / importance / relevance` 的来源。我们的 `recency()`（7 天 1.2、30 天 1.0、更早 0.85）和 `importance` 加权（`1 + 0.3 * imp`）就是从这来的，**但权重是我们自己调的，不是论文原值**。
  - <https://arxiv.org/abs/2304.03442>

## 3. 写入策略（`90` §4 的 ADD / UPDATE / DELETE / NOOP）

- **Mem0**（arXiv 2504.19413）—— 写入时先判「新信息相对旧记忆该 ADD 还是 UPDATE / DELETE / NOOP」，避免同一件事记十遍。我们的槽位（`〔槽位: 城市〕`）与 TTL 改写就是这条的土办法版。
  - <https://arxiv.org/abs/2504.19413>
  - 工程侧：<https://docs.mem0.ai>
- **Reflexion**（arXiv 2303.11366）—— 把失败写成人能读的反思再回灌。我们的 `82-重复问题台账` + `83-自维护` 是同一思路：**同一个坑踩第二次就落一条规则**，只是没用模型自动生成，靠我手写。
  - <https://arxiv.org/abs/2303.11366>

## 4. 我们故意的偏离（别拿论文来纠正我）

| 论文做法 | 我们为什么不做 |
| --- | --- |
| 向量 / embedding 检索 | 零依赖红线（`SKILL.md` §1）：不装库、不联网、不额外跑模型；「意思相近但字不沾边」查不到就靠同义词组 `tools/synonyms.py` 近似，真语义不做 |
| 自动把记忆搬进搬出上下文 | **写入永远自动开**（2026-10-20 死规矩，见 `SKILL.md` §6）：聊到就写，拿不准扔 `_待确认.md`，只有用户说「不用记 / 忘掉」才停；检索那一端仍是闸门控制——写得多不等于每轮都塞进上下文 |
| BM25 全套（tf 饱和 + 长度归一化） | `memdb.py` 行级那套没上，靠 `df` 权重够用；**片段层 `frag.py` 已上全套**（1～4 行短片段，长度惩罚不会误伤） |
| BM25+ 的 `δ` 下界项 | 片段短、长度差小，下界缺陷不明显；等片段变长再加 |
| 自己训 embedding / 让大模型做 query rewriting | 本机没有轻量中文 embedding；每次检索都过一次大模型太贵，同义词组是它的土办法版 |
| 让模型自己反思生成规则 | 规则只从「真踩过的坑」来，模型自己编的规则容易自我强化 |

## Claude Code 的记忆怎么做（2026-10-20 查证）

来源：https://code.claude.com/docs/en/memory （官方文档）

- **手写指令四层**：企业级 `C:\Program Files\ClaudeCode\CLAUDE.md` → 用户级 `~/.claude/CLAUDE.md` → 项目级 `./CLAUDE.md` 或 `./.claude/CLAUDE.md` → 本地 `./CLAUDE.local.md`（进 `.gitignore`）。启动时把工作目录**及所有上级目录**的全部拼接注入（不覆盖）；子目录的物理上等真碰到那个文件时才读。
- **`@path` 引用**：最深 4 层递归；路径含空格要每个空格前加反斜杠；代码块与反引号内的 `@` 不解析。块级 HTML 注释 `<!-- -->` 在注入前被剔掉，属于「不占 token 的维护笔记」。
- **`.claude/rules/`**：一主题一文件，frontmatter 用 `paths:` 做路径域限定，动到匹配文件才加载；没 `paths` 的随启动加载。
- **自动记忆（auto memory）**：存在 `~/.claude/projects/<项目>/memory/`，结构是「一个 `MEMORY.md` 索引 + 每主题一个文件」；写入分四类 `type`：`user` / `feedback` / `project` / `reference`；它会主动跳过能从代码里推出的东西，也跳过 CLAUDE.md 已经说过的。
- **加载策略是这件事的核心**：启动只读 `MEMORY.md` 的**前 200 行或 25 KB**（先到者为准），主题文件一律不进上下文，等需要时用普通文件工具打开——即 `lazy load`（懒加载）。超过上限时写入还会成功，但下次加载会丢掉超出部分并报错要求重写索引；写入时会自动记一个 `modified` ISO 时间戳。
- **它根本没有检索引擎**：零打分代码。解法是「短索引常驻 + 模型自己用眼睛翻」，猜错了再开一篇，成本一次工具调用。
- **我们可以借鉴的一条**：把现在的「495 个片段 + SQLite 打分 + 钩子按轮次投喂」，换成「一百多行记忆目录常驻 + 需要细节时自己开文件」。用户感觉「命中率低」，很大程度是因为我们把它做成了有损的自动投喂，不是让模型看见目录。
- **故意不跟**：它的四层 CLAUDE.md 拼接对单人单机过重（我们已有工作区 `AGENTS.md` 常驻）；企业 managed policy 层用不上。
